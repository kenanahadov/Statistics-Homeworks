From a wallet seed to an Ethereum address

Hashing, key derivation and public-key cryptography: the role of each step and its statistical properties.

1. Aim and wallet pipeline

This report explains a common mnemonic-based Ethereum wallet pipeline for an externally owned account. The starting point is securely generated random data. A mnemonic makes backup easier, while deterministic derivation allows the same keys to be recovered later.

Random entropy → Mnemonic
↓ BIP-39: mnemonic + optional passphrase

↓ BIP-32 derivation along a BIP-44 path

BIP means Bitcoin Improvement Proposal; EIP means Ethereum Improvement Proposal. The BIP wallet conventions can also be used for Ethereum. They organize wallet recovery and keys; they are not all requirements imposed by the Ethereum network.

2. What each component does

BIP-39 — mnemonic and seed

BIP-39 encodes 128–256 bits of random entropy, plus a SHA-256-based checksum, as 12–24 words from a 2,048-word list. For example, 128 entropy bits plus 4 checksum bits give 132 bits, represented by twelve 11-bit word indices.

The mnemonic and an optional passphrase are then processed with PBKDF2-HMAC-SHA-512 using 2,048 iterations to derive a 512-bit seed. The passphrase is an additional input, not an extra mnemonic word. The same mnemonic and passphrase always produce the same seed.

BIP-32 — hierarchical deterministic keys

BIP-32 uses HMAC-SHA-512 to derive a master private key and a chain code from the seed. Child keys form a tree, with the chain code providing additional derivation data. One seed can therefore restore many accounts. The derivation is deterministic: it does not generate fresh random entropy at each branch.

BIP-44 — organizing the tree

BIP-44 specifies the path structure m / purpose' / coin_type' / account' / change / address_index. A common first Ethereum address uses m/44'/60'/0'/0/0: 44 identifies the convention, 60 identifies Ethereum, and the remaining zeros select the first account, external branch and first address. An apostrophe marks hardened derivation, which requires the parent private key. Wallets can use different paths, so the path matters when restoring an account.

secp256k1 — private key to public key

A valid private key is a scalar k with 1 ≤ k < n, where n is the order of the standard base point G. The public key is the curve point Q = kG. This is the same idea as Homework 1, using much larger parameters. Recovering k from Q and G is believed computationally infeasible. Ethereum uses ECDSA on this curve to sign transactions and verify authorization; scalar multiplication itself is neither hashing nor encryption.

Keccak-256 — public key to address

Hash the 64-byte public-key coordinates x || y, excluding the uncompressed key's initial 04 byte. Keccak-256 produces a 32-byte digest. Its last 20 bytes form the 160-bit address, normally written as 40 hexadecimal characters with an 0x prefix. An address is therefore different from the full public key.

EIP-55 — address checksum

EIP-55 hashes the lowercase hexadecimal address text without 0x, using Keccak-256. Each address letter is capitalized when the corresponding hash digit has value 8 or greater; numerical digits stay unchanged. A wallet that checks this capitalization can detect many typing mistakes. It does not change the 20 address bytes or prove ownership.

4. Statistical properties

Entropy and determinism

With uniformly generated 128-bit entropy, each initial bit string has probability 2−128. Encoding it as twelve words does not add randomness: the checksum constrains valid phrases. A 512-bit seed is an output length, not a guarantee of 512 bits of entropy. With a fixed passphrase, deterministic processing cannot increase the entropy of the original secret.

Derived keys are intended to be computationally unpredictable without the necessary secret information, although they remain mathematically related. Repeating the same mnemonic, passphrase and derivation path produces the same key and address. Random-looking outputs do not imply statistical independence from their inputs.

Bit frequencies and avalanche behaviour

For varied inputs, a secure hash is expected to behave approximately like a uniform mapping: each output bit should be close to equally likely to be 0 or 1. Flipping one input bit should change about half of the hash output bits on average—about 128 of 256 for Keccak-256. This is an expectation over many comparisons, not a rule for every pair.

In an experiment, each generated output would be a statistical unit. A selected bit would be a binary variable, and its relative frequency of ones would be the number of ones divided by the number of outputs. Observed frequencies fluctuate around theoretical probabilities. This report discusses expected properties; it does not report measured simulation results.

For secp256k1, uniformly selected valid scalars give uniformly distributed non-identity points in the subgroup generated by G. Their coordinates remain constrained by the curve equation. Hash-style avalanche behaviour is not the basis of elliptic-curve security, which relies on the difficulty of the discrete logarithm problem.

Collisions and error detection

Under an ideal uniform-address model, two independently generated addresses match with probability 2−160. Among N addresses, the expected number of matching pairs is N(N − 1)/(2 × 2160), so collision risk grows with the number of pairs. Collisions are possible even when extremely unlikely for ordinary use.

EIP-55 adds error detection through letter case, not extra address entropy. Some mistakes can pass the checksum, and a valid checksum does not establish that an address belongs to the intended recipient. Balanced bits, low observed correlations or an absence of collisions in a small sample do not prove cryptographic security.

5. Historical context and hash families

DateDevelopment
1977RSA introduced public-key encryption and signatures based on different mathematics from elliptic curves. It is historical context, not a step in this wallet pipeline.
2001–2002SHA-2, including SHA-512, emerged around 2001; the final FIPS 180-2 standard was published in 2002.
2012BIP-32 proposed hierarchical deterministic wallets.
2013BIP-39 proposed mnemonic-based seed generation.
2014BIP-44 proposed standard multi-account derivation paths.
2015NIST standardized SHA-3, based on Keccak, which had been selected in 2012.
2016EIP-55 proposed mixed-case Ethereum address checksums.

SHA means Secure Hash Algorithm. SHA-512 belongs to SHA-2 and appears inside HMAC in BIP-39 and BIP-32. SHA-3 is a separate family based on Keccak's sponge construction; it is not a version of SHA-512. Ethereum's Keccak-256 and standardized SHA3-256 both return 256 bits, but their domain-separation/padding conventions differ, producing different digests. SHA3-256 cannot be substituted for Keccak-256 in Ethereum address derivation.

6. Why use several techniques?

BIP-39, BIP-32 and BIP-44 make keys recoverable and organized. secp256k1 provides the public/private-key relationship and supports signatures. Keccak-256 supplies hashing for address derivation, while EIP-55 helps detect transcription errors. A hash alone cannot sign a transaction, and a checksum cannot manage a key tree. Combining these components gives each task an appropriate method.
